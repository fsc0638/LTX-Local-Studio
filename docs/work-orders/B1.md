## 已完成

### (1) 三表 migration

- `projects`／`shots`／`takes`，欄位照規格。形狀跟著 A1 的工作單 v2 走（`bible`、`request`、
  `pinned` 就是匯出格式帶的那份 JSON），所以計畫可以原樣往返 API。
- `status` 與 `verdict` 用 CHECK 約束綁死合法值，與 `lib/production-factory.ts` 的
  `FactoryRunState`／`FactoryShotState` 對齊。
- `shots.idempotency_key` 全表唯一 —— 那把鑰匙正是「重送不會再燒一次 GPU」的依據。
- 外鍵語意刻意分兩種：
  - `shots.project_id`、`takes.shot_id` 用 `ON DELETE CASCADE`：刪專案就整條帶走。
  - `takes.job_id` 用 `ON DELETE SET NULL`：走既有的可復原刪除流程移除成品時，take 的評語與
    裁決要留著，只是不再指向 job。
- 索引：`projects(owner_id, updated_at)`（租戶邊界，每次列表都用）、`shots(project_id, position)`、
  `shots(status, project_id)`（排程器找下一鏡）、`takes(shot_id, created_at)`、`takes(job_id)`。

實測（`ltx_studio_test`，交易內驗完即 rollback）：

```
apply_migrations() 第一次 → ['0002_factory.sql']，第二次 → []（冪等）
刪 job    → take 還在、job_id 變 NULL          （ON DELETE SET NULL 生效）
刪 project → shots=0 takes=0                    （CASCADE 生效）
status='bogus'      → violates check constraint "projects_status_check"
project_id 不存在   → violates foreign key constraint "shots_project_id_fkey"
```
