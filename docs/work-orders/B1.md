  - `takes.job_id` 用 `ON DELETE SET NULL`：走既有的可復原刪除流程移除成品時，take 的評語與

- 索引：`projects(owner_id, updated_at)`（租戶邊界，每次列表都用）、`shots(project_id, position)`、

### (2a) 資料層 `factory_store.py`

規格的端點與排程迴圈需要一個能獨立測試的資料層，先做它。

- `FactoryStore` 的回傳就是 v2 工作單的形狀（camelCase，含 `format`／`version`／`bible`／`shots`），
  瀏覽器不必再學一套格式；接受的也是匯出格式產生的東西。
- **租戶邊界貫穿每一個方法**：`owner_id` 不符一律回 `None`，不是回空資料再靠上層過濾。
- `replace_shots()` 是整份取代而非逐鏡 patch：瀏覽器把計畫當一個單位編輯（重排、合併、拆分），
  一次原子替換勝過一串可能半途留下 position 空洞的 patch。
- **一個交易的三處更新**：`record_take()` 同時寫鏡狀態、take 與 job 連結，必要時一併暫停專案。
  鏡頭已標 failed 但專案還讀作 running 的話，排程器會繼續送下一鏡 —— 所以必須同交易。
- `next_queued_shot()` 用 `FOR UPDATE ... SKIP LOCKED`，兩個排程輪次不會搶到同一鏡。
- `pause()` **不動已在 GPU 上的鏡頭**（只把 `queued` 退回 `draft`）：暫停不該丟掉快做完的工作。
- `recover()` 給 API 重啟用：把 `validating`／`submitting`／`running` 退回 `queued`，
  **冪等鍵不變**，所以真的送達 worker 的任務是被重播而非重跑。

`tests/test_factory_store.py`：12 項，涵蓋租戶隔離、prompt 驗證、start／pause 語意、
排程取用順序、失敗同時停線、成品與 take、重啟續跑保留冪等鍵、佇列計數、刪除連帶。

`tests/conftest.py` 的 TRUNCATE 清單補上 `projects`／`shots`／`takes` —— 少了它們，
前一個測試的資料會漏進下一個（實際踩到，兩個測試因此誤判）。

### (2b)(2c) 端點與排程迴圈

端點（全部在 `/api/v1/` 之下，沿用既有的 worker 憑證與 Origin 檢查）：

| 方法 | 路徑 |
|---|---|
| GET／POST | `/api/v1/factory/projects` |
| GET／POST／DELETE | `/api/v1/factory/projects/{id}` |
| POST | `/api/v1/factory/projects/{id}/shots`（整份取代） |
| POST | `/api/v1/factory/projects/{id}/run`、`/pause` |
| GET | `/api/v1/factory/shots/{id}/takes` |

- **租戶**：`owner_id` 取自 `principal["id"]`；service 憑證沒有帳號，用哨符 `@service`
  （真實 user id 是 32 位十六進位，不會碰撞）。
- **配額**：`LTX_FACTORY_QUEUE_LIMIT`（預設 100）在 `/run` 時檢查，超過回 429。
- **排程迴圈** `factory_scheduler()`：每個 running 專案先收攏已在 GPU 上的鏡頭，再送下一鏡；
  一次一個 GPU 名額。狀態全在 PostgreSQL，所以關掉所有瀏覽器不影響，重啟也從同一點續跑。
- **只編排**：`factory_send()` 走的是 `worker.validate_request` → `worker.parse_request` →
  `submit_job`，與 HTTP 送單完全同一條路，沒有私有捷徑。
- `worker_busy` → 鏡頭退回 `queued` 保留順位，下一輪再試（不算失敗）。
- worker 拒絕的請求（`ValueError`）→ 標 failed 並暫停整條線：重試也不會變成功，要人處理。
- 啟動時 `FACTORY.recover()` 把 mid-flight 鏡頭退回 `queued`，冪等鍵不變。

`tests/test_factory_api.py`：16 項，含 v2 往返、匯入含鏡頭、prompt 驗證、run/pause 語意、
404 而非錯誤、刪除、takes 列表、**worker_busy 保留順位**、**拒絕請求停線**、
**送出後與 job 連結並隨之結案**、**重啟從資料庫續跑且冪等鍵不變**。

### (3) 對外契約

規格寫「`worker_schema.py` 的 v2 伺服器端驗證」，但該檔其實是 **OpenAPI 文件產生器，不是驗證器**。
實際的輸入驗證已經在 `factory_store.py`（`_request`／`_title`／`_pinned`／`_bible`），所以這一步做的是
把 v2 形狀寫進對外契約，讓上游能照著建計畫。

新增 `FactoryPlan`／`FactoryShot`／`FactoryTake` 三個 schema 與 6 條路徑。
`FactoryShot.request` 直接 `$ref` 既有的 `JobRequest` —— 一鏡的 request 就是一份完整的
`/api/v1/jobs` body，不是另一種格式。上限值（`MAX_TITLE`／`MAX_SHOTS`／狀態列舉）從
`factory_store` 取，避免文件與實作各說各話。

### (4) 前端改讀寫 API

- `lib/factory-client.ts`（新）：型別化的 `/api/v1/factory` 客戶端。所有回傳計畫的路徑都經過
  `restoreFactoryPlan`，格式壞掉在這裡就被擋下，不會滲進 render tree。
- **瀏覽器不再驅動佇列。** 原本那段 165 行的 validate → submit → poll 迴圈整段移除，換成
  `plan.status === 'running'` 時每 2 秒重讀專案。關掉分頁不再停止生產 —— 這正是把佇列搬到主機的目的。
- 編輯是本地樂觀更新 + 600ms 後同步（`dirty` 旗標），打字不會每個鍵一個請求。
  **產線執行中不推送**：那時主機才是計畫的擁有者，推送會蓋掉它正在寫的進度。
- 按下開始前會先 flush 未同步的編輯 —— 否則會拿主機沒看過的舊鏡頭去跑。
- **舊計畫搬移**：偵測到 pre-B1 留在 localStorage 的計畫時顯示橫幅，讓使用者選擇上傳或捨棄。
  **不自動上傳** —— 那可能是他已經放棄的計畫。上傳保留鏡頭與冪等鍵。三語文案齊全。
- 時間格式對齊：API 改回 ISO 字串（`_iso()`），與 A1 凍結的 v2 格式一致。
  先前回 epoch 數字，`restoreFactoryPlan` 只接受字串，會靜默丟掉時間戳。
