# D4 工站排程與 LP 預算

規格：`docs/PRODUCTION_ROADMAP.md` 的 D4 節。分支 `wo/d4`。

## 已完成

- `station_scheduler.py` — 純規則：模型 → 工站（`ltx`／`imagegen`／`none`，優先看 adapter 的 `gpu_tenant`）；
  `choose_next`（GPU 上的工站先做、否則佇列最多的工站先做、後製不等它不需要的切換）；`group_by_station`／
  `switch_count`；`estimate`（Σ 每鏡秒＋切換次數×目的工站載入秒＋OpenAI tokens，**列出哪些模型用了預設值**）；
  `budget_warnings`（只警告）。預設值來自 `docs/GB10_SETUP.md` 與 D1 量測（Qwen 載入 336 s／25.8 s、Z-Image 12.9 s）。
- `factory_store.py` — `queued_models`、`inflight_any`、`remaining_models`、`project_runtime_seconds`、
  **`next_queued_shot_for(project, models)`**：同一計畫裡混著關鍵格與鏡頭時，排程器能拿「該工站的下一鏡」而不是
  「位置上的下一鏡」——沒有這個，12＋12 會切 23 次（第一版測試抓到的）。
- `local_backend.py` — `scheduler_pick()`（可測、不送 job）：GPU 上的工站優先，否則佇列最多的工站；每個計畫先給
  該工站的下一鏡。`factory_scheduler` 改用它，全域一次一個 job。
  `GET /api/v1/factory/workstation`（誰坐 GPU、依工站的佇列、正在跑的、切換代價與排空 ETA、滾動平均與預設）、
  `GET /projects/{id}/budget`（預估、實花、預算、警告）。
- `production_store.py` — `average_runtime(model)`：最近 20 個成功 job 的 `runtime_seconds` 平均（欄位本來就在 snapshot 裡）。
- Bible 多 `budget: {gpu_seconds?, openai_tokens?}`（TS 白名單與型別）。
- `components/workstation-panel.tsx` — 接進既有「工站」分頁上方：GPU 現況、依工站佇列、正在跑、切換代價／排空 ETA、
  本專案預算（預估拆解、實花、assumed 標示、超預算警告）、預算表單。三語。每 5 秒輪詢。
- 測試：`tests/test_station_scheduler.py`（9，純）、`tests/test_workstation.py`（7，真 store 驅動 `scheduler_pick`）。
  **12 張關鍵格＋12 鏡 LTX 恰好切換 1 次**在純規則與真 store 兩層都有；跨計畫時 GPU 上的工站先排空；預算超了仍能 `/run`。
