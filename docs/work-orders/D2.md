# D2 關鍵格階段

規格：`docs/PRODUCTION_ROADMAP.md` 的 D2 節。分支 `wo/d2`。

## 已完成

- `db/migrations/0006_keyframes.sql` — `keyframes` 表（每個候選一列，重生是第二列不是覆蓋）、`projects.keyframe_run`。
- `lib/keyframes.ts` — 純規則、零 import：綠（≥線）／黃（線下 0.05 內）／紅；紅**只自動重生一次**（換 seed，
  由原 seed 推導、可重現）；批次估時＝一次切換 336 s＋每鏡 26 s；磁貼顯示哪個候選；哪些鏡需要人。
  `tests/keyframes.test.mjs`（6）。
- `lib/stages.ts` — `keyframes` 不再「本期未啟用」，但它是**可略過的**：idle 時不會成為「你在這裡」，
  只有候選等人時才 attention；全部鏡都來自核准關鍵格時 done。`progressOf` 加 `extras` 讓關鍵格頁回報 attention 數。
  `tests/stages.test.mjs`（+2）。三語 `nextKeyframes`／`nextKeyframesReview`。

- `factory_store.py` — keyframes CRUD、run 狀態、`approve_keyframe`（`request.image_id`＝提升後的 asset、
  `request.keyframe_id`、pin `image_id`；先前核准的候選標 superseded）、`reject_keyframe`（必填原因）。
- `local_backend.py` — `keyframe_batch` 單執行緒整批：每鏡 `select_reference` 依 angle 選參照（沒選到且鏡沒有
  `image_id` 時退回 Bible 第一張，與前端投影一致）→ Qwen edit job 走既有 admission（LTX 佔 GPU 時等 `worker_busy`
  而不是失敗）→ 等完成 → judge → `review_rules.keyframe_light`（綠／黃／紅，黃帶 0.05）→ 紅換 seed 重生**一次**
  → 記錄；沒參照的鏡單獨 failed、批次繼續。`promote_keyframe_asset` 用與上傳相同的驗證與 sidecar 把 PNG 提升為
  真 asset。端點：`GET /projects/{id}/keyframes`（含 run、gpu、costs）、`POST …/keyframes/run|stop`、
  `POST /keyframes/{id}/approve|reject`。
- `components/keyframes-board.tsx` — 縮圖格（每鏡顯示核准／最新候選）、燈號與說明、核准／退回、
  「產生全部關鍵格」／停止、**階段提示**（影像模型常駐＝關鍵格階段；未載入＝拍攝階段）與**切換代價**
  （336 s＋每鏡 26 s，模型已常駐時不算切換）；生成中每 3 秒輪詢。`app/page.tsx` 02 分頁；三語。
  03 拍攝的鏡頭列多「來自關鍵格」籤（`request.keyframe_id`）。關鍵格頁把待人決定的數量回報給階段導覽。
- `tests/test_keyframes.py`（13）：真 imagegen 服務模組 FAKE 模式＋腳本化 judge，走 admission → client 子程序
  → 租約 → 判分 → 重試 → 提升為 asset（他人帳號 404）。測試裡把 `submit_job` 包成「admission 後同步跑 job」，
  因為 fixture 把背景 job 執行緒 stub 掉了（`run_job_implementation` 的慣例）。
