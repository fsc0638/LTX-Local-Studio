# D1 imagegen adapter 與 GPU 租約

規格：`docs/PRODUCTION_ROADMAP.md` 的 D1 節。分支 `wo/d1`。

## 已完成

- `local_adapters/imagegen.py` — `qwen-image-edit-2509`（mode `edit`，需 `image_id`，可加 `reference_2/3`）與
  `z-image-turbo`（mode `generate`，不收圖）。參數 `steps`（預設 8）、`seed`、`size`（enum）、`lightning`、
  `reference_2/3`（asset id）——全部經 `model_registry.normalize` 檢查，**沒有任何參數是路徑**。
  adapter 的 argv 是 `services/imagegen/client.py`（LTX venv、純 stdlib），參照圖的私有路徑由 API 解析後
  透過 `LTX_IMAGE`／`LTX_IMAGE_2`／`LTX_IMAGE_3` 交給它。
- `model_registry.py` — `load_installed()` 也註冊模組的 `EXTRA_ADAPTERS`（一個模組一個家族）；
  `edit` 模式與 `i2v` 一樣要求 `image_id`。
- `local_backend.py` — `job_environment` 解析 `reference_2/3`；`submit_job` 對它們做所有權檢查；
  **`run_job` 在生成前取得 GPU 租約、結束後釋放**；loopback `GET /api/internal/gpu-lease`。
- `gpu_lease.py` — 佇列本來就一次一個 job，租約補的是 job 之間**留在記憶體裡的東西**：
  LTX 開跑前逐出常駐的 imagegen 模型（`POST /release`）並等 `/health.loaded` 變空；imagegen 開跑前確認沒有
  LTX job。服務沒在跑＝沒持有記憶體；服務不放手＝逾時拒絕 LTX 開跑（寧可重試不要 OOM）。
  裁判、音訊、後製不是租約對象。
- `services/imagegen/server.py` — 8792、只綁 loopback；**同時只常駐一個模型**（Qwen 61 GB＋Z-Image 23 GB
  不能並存），換模型先卸載；閒置 `LTX_IMAGEGEN_IDLE_MINUTES`（預設 10）後釋放；`/release`；`/progress/<id>`；
  `/generate` 一次一張（第二個請求排隊，不並發）；**載模型前先問 ltx-api 的 `active-jobs`**，
  問不到當作忙（錯判「空閒」的代價是 OOM，錯判「忙」的代價是重試）。`LTX_IMAGEGEN_FAKE=1` 用假 pipeline。
- `infra/systemd/ltx-imagegen.service` — 只建檔，`Environment=` 含空格已加引號，`HF_HUB_OFFLINE=1`，
  `systemd-analyze --user verify` 輸出為空。
- 測試：`tests/test_gpu_lease.py`（9，假工站）、`tests/test_imagegen_adapter.py`（12，真服務模組的 FAKE 模式
  在程序內起在隨機 port，走完整的 admission → client 子程序 → 租約 → PNG 技術檢查 → 私有 artifact）。
  含「20 張只付一次載入」與「換模型會卸載另一個」。
